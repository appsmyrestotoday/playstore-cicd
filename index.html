Google Cloud

Enable the Google Play Developer API

Every automated release goes through this API. It has to be switched on for the Cloud project that will hold the service account, before anything else works.

GCP Console → APIs & Services → Library → "Google Play Android Developer API" → Enable
✅ Already done for this project — confirmed working when the service account began appearing in Play Console's user list.
2
Google Cloud

Create the service account

A dedicated machine identity — play-release-bot — that GitHub Actions authenticates as. It never logs in as a person; it only has the permissions explicitly granted to it.

IAM & Admin → Service Accounts → Create service account
  1. Service account name: play-release-bot
  2. Description: admin app ixpos by myResto Today
  3. Google generates the unique email — play-release-bot@project-4f10bdbd-d058-4a3f-be3.iam.gserviceaccount.com — this is the identity used everywhere downstream.
3
Manual fix required

Org policy blocked key creation — override it

GCP's default security baseline blocks downloading service account JSON keys via the iam.disableServiceAccountKeyCreation org policy. This had to be explicitly overridden for the project before a key could be issued.

IAM & Admin → Organisation Policies → "Disable service account key creation" → Add a rule → Enforcement Off → Set policy
⚠️ This step needs Organization Policy Administrator rights. If you can't see this option, it's because someone else administers the Google Workspace/Cloud org — ask them to disable the constraint, ideally scoped to just this project rather than org-wide.
4
Google Cloud

Generate and download the JSON key

The actual credential file GitHub Actions will use to authenticate as play-release-bot. It's a private key — treated as a secret from the moment it lands on disk.

Service account → Keys → Add key → Create new key → JSON → file downloads automatically
🔒 This file grants access to your Cloud resources. Move it straight into a GitHub secret (Step 6), then delete the local copy — don't leave it sitting in Downloads or commit it to a repo.

Repo config

Wire signing into build.gradle

The build needs to know how to sign the release .aab using the keystore, reading the passwords from environment variables rather than hardcoding them.

gradle bundle release → produces the signed Android App Bundle Fastlane will upload
android/app/build.gradle 
android {
    defaultConfig {
        applicationId "com.myrestotoday.ixpos"
        versionCode 12
        versionName "1.3.0"
    }
    signingConfigs {
        release {
            storeFile file("release.keystore")
            storePassword System.getenv("KEYSTORE_PASSWORD")
            keyAlias System.getenv("KEY_ALIAS")
            keyPassword System.getenv("KEY_PASSWORD")
        }
    }
    buildTypes {
        release {
            signingConfig signingConfigs.release
            minifyEnabled true
        }
    }
}
8
Repo config

Define the Fastlane deploy lane

Fastlane is the glue: it bumps the version, builds the bundle, and calls the Play Developer API to upload it — all from one command GitHub Actions can run.

fastlane deploy — one command chains all three actions
android/fastlane/Fastfile 
default_platform(:android)

platform :android do
  desc "Deploy iXpos to Play Store"
  lane :deploy do
    increment_version_code(gradle_file_path: "app/build.gradle")

    gradle(
      task: "bundle",
      build_type: "Release"
    )

    upload_to_play_store(
      package_name: "com.myrestotoday.ixpos",
      track: ENV["PLAY_TRACK"] || "internal",
      aab: "app/build/outputs/bundle/release/app-release.aab",
      json_key: "play-service-account.json",
      release_status: "completed",
      skip_upload_metadata: true,
      skip_upload_images: true,
      skip_upload_screenshots: true
    )
  end
end
9
GitHub Actions

The workflow that ties it all together

Triggered by a version tag (or manually), this workflow decodes the secrets, runs the Fastlane lane, and ships the build — with a manual approval gate for production.

.github/workflows/release-ixpos.yml — each box is a job step; the last gate needs a human click for production
.github/workflows/release-ixpos.yml 
name: Release iXpos to Play Store

on:
  push:
    tags:
      - 'ixpos-v*'
  workflow_dispatch:
    inputs:
      track:
        description: 'Play track'
        default: 'internal'
        type: choice
        options: [internal, alpha, beta, production]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: play-production
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '17' }
      - uses: ruby/setup-ruby@v1
        with: { ruby-version: '3.2', bundler-cache: true }
      - run: gem install fastlane
      - run: echo "${{ secrets.ANDROID_KEYSTORE_BASE64 }}" | base64 -d > android/app/release.keystore
      - run: echo '${{ secrets.PLAY_SERVICE_ACCOUNT_JSON }}' > android/play-service-account.json
      - name: Deploy
        working-directory: android
        env:
          KEYSTORE_PASSWORD: ${{ secrets.ANDROID_KEYSTORE_PASSWORD }}
          KEY_ALIAS: ${{ secrets.ANDROID_KEY_ALIAS }}
          KEY_PASSWORD: ${{ secrets.ANDROID_KEY_PASSWORD }}
          PLAY_TRACK: ${{ github.event.inputs.track || 'internal' }}
        run: fastlane deploy

Rollout

Track progression, from internal to production

iXPOS is already live on the Production track with 3 installs. Going forward, the safe pattern is to let new tags land on a lower track first, and gate Production behind a manual approval.

Recommended flow: automate the first two hops fully, keep a human click before Production
  1. Push a version tag → pipeline deploys to Internal automatically, every time.
  2. Promote to Beta once internal testers confirm the build.
  3. Trigger Production via workflow_dispatch, gated by a GitHub Environment reviewer — even once the mechanics are trusted, keeping a manual click here limits the blast radius of a bad release.
