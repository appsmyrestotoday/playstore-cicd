Login API Specification & Data Models

Official technical documentation for the authentication endpoint of the iXPOS Windows Desktop Application by myResto Today. Specifies response structures, data models, subscription status enums, and error handling contracts.

Core Development Rules & Specifications

1. Strict Envelope Uniformity

Do NOT change the response body structure between successful and failed authentication attempts. The top-level schema keys must always remain identical across all status codes.

2. Handling Failed Logins

On authentication failure (success: false), set login_context_and_data strictly to null. Detailed diagnostic info must be provided in the error object.

3. Deterministic Active Status Enum

active_status.method uses a fixed enum (DATE or PURCHASE). Frontend applications inspect this field to determine subscription validity and display logic.

Key Architectural Refinements

1. Disambiguated User vs. Brand Name

Removed duplicate name key inside account. name is designated specifically for User Name (e.g. "Ahinas"), while brand_name stores the Brand Name.

2. Multi-Store Support (stores[])

Replaced single store object with an array stores[] to accommodate brands managing multiple store outlets.

3. Structured Store Sub-Objects

Every store item in stores[] embeds 2 dedicated sub-objects: active_status (subscription state) and location (address details).

4. API-Friendly English snake_case

Removed all non-English / Malayalam key names. Replaced with standardized snake_case field names (e.g., wallet_coin_balance).

5. Total Brand Stores Counter

Added store_count_under_this_brand in account to report total registered store outlets managed under the brand entity.

6. Non-Brand Account Nullability

When is_brand is false, brand fields brand_name and brand_logo_url automatically evaluate to null.

7. Conditional Method Payload Fields

date and purchase fields are evaluated based on active_status.method (DATE populates date; PURCHASE populates purchase).

8. Strictly-Typed Numeric Values

Stored commission_rate (e.g., 0.11) and balances as native JSON numbers instead of strings for precision arithmetic in client apps.

Data Models Breakdown

Top-Level Response Envelope

Root JSON Object
Field Name Data Type Nullable Description & Frontend Behavior
success boolean No Indicates authentication outcome. true if authorized; false on failure.
message string No System/debug summary string (e.g., "Login successful" or "Login failed").
ui_message string No User-facing notification banner text formatted for display in client UI.
login_context_and_data object Yes Contains user account metadata and accessible stores array. Set strictly to null on login failure.
redirect_url string No Target routing path for client navigation (e.g. /dashboard on success, /error-page on failure).
error object No Error details object. Fields are null when success = true.

Account Model (login_context_and_data.account)

User Identity & Brand Organization
Field Name Data Type Nullable Description & Frontend Behavior
id string No Unique user account UUID.
user_type string No User classification type (e.g. "admin", "cashier").
name string No User Display Name (e.g. "Ahinas"). Disambiguated from brand_name.
email string No User email address.
mobile string No User mobile phone number including country code.
avatar_url string Yes User profile picture URL (or null if unassigned).
role string No System access permission role (e.g. "ADMIN", "MANAGER").
is_brand boolean No Flag indicating if account operates a multi-store brand organization.
brand_name string Yes Name of the brand entity. Evaluates to null if is_brand == false.
brand_logo_url string Yes Brand logo image URL. Evaluates to null if is_brand == false.
store_count_under_this_brand integer No Total number of registered store outlets managed under this brand organization.
is_brand_verified boolean No Brand verification status flag.
is_user_verified boolean No User identity verification status flag.

location object No Store location address and geolocational coordinates.

Subscription Active Status Enums (active_status.method)

To make subscription evaluation clean and predictable for the frontend client, active_status.method relies on a fixed enum: DATE or PURCHASE. The client inspects method to decide whether to render the expiration date or minimum purchase quota.

Method Enum: "DATE" Date-based Subscription 
{
  "method": "DATE",
  "date": "2028-08-12",
  "purchase": null,
  "wallet_coin_balance": 126,
  "commission_rate": 0.11,
  "exchange_currency": "INR"
}
When method == "DATE", date contains the expiration date string (YYYY-MM-DD) and purchase is set to null.
Method Enum: "PURCHASE" Purchase-volume Subscription 
{
  "method": "PURCHASE",
  "date": null,
  "purchase": 120458,
  "wallet_coin_balance": 126,
  "commission_rate": 0.11,
  "exchange_currency": "INR"
}
When method == "PURCHASE", purchase contains the required purchase quota number and date is set to null.
